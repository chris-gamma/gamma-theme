The soft launch is planned for February 2027 and the grand opening for April 2027.

- Primary, the production store, is `location-gamma.myshopify.com` (permanent domain `d2e135-ff.myshopify.com`, shop ID 74939334829). It is password-protected until launch.

From release on, the live theme won't follow `dev`: pushing `dev` updates only the development setup, and releases reach the live store separately. Don't conclude from the current setup that `dev` is or will be the live theme.

## Scope and decisions

- Work inside this repository. Preserve existing edits, historical commits, vendor tags, attribution and [LICENSE.md](LICENSE.md). Branches, integration and commits follow [Branches and commits](#branches-and-commits).
- Make minimal, targeted changes. Preserve deliberate Gamma customizations; inspect relevant code and history before replacing them. Avoid unrelated refactors, dependency changes, formatting or file edits.
- Resolve technical decisions in this order: explicit user instructions; current Shopify platform requirements and supported behavior; Horizon architecture and conventions; Gamma's established conventions and customizations; general development practices. Identify conflicts explicitly. This order does not authorize unsupported or unsafe implementations, or replacing working Gamma behavior merely because a newer pattern exists.
- Establish whether the task is planning, reviewing, or implementing. Planning and review are read-only unless implementation is explicitly requested: inspect relevant evidence without branch changes, dependency installation, file edits, commits or store mutations. Before implementing, identify the requested outcome, applicable approvals, dependencies, affected surfaces and observable acceptance criteria.
- Do not attempt to resolve bugs or issues in upstream Horizon code. Focus on authorized changes within the Gamma project scope. Do not introduce workarounds or modifications for upstream issues unless explicitly authorized. Review and report upstream issues in the response as appropriate.
- Keep work local. [Store access](#store-access) is the authority for every store operation, including development and unpublished themes: its one standing exception is the Gamma-Dev preview, and everything else needs explicit authorization for that exact operation. External service writes and hosting operations also require authorization. Confirm the exact store and operation before an authorized write; never infer a store from a branch name or assume authorization carries over from an earlier task.
- Do not add hooks, scripts, skills, workflows, CI or agent tooling unless explicitly requested or authorized; the skills in `.agents/skills/` are the authorized exception and may be kept current. The buildless-maintenance rule below authorizes relevant local configuration, npm check commands and development dependencies; other tooling still requires explicit authorization.

## Branches and commits

- Each piece of work gets one branch, and you name it yourself: a type prefix for what the change does, then a short kebab-case name of its area and scope (two to four words) that no existing branch uses. Say which name you chose when you start. A branch in the development plan's tables keeps the name the plan gives it, and a new row is named by the same rule.
  - `feature/`: new or changed storefront behaviour, design or content contracts, such as `feature/design-cart`. Add the work to the plan's tables first.
  - `fix/`: corrects a defect in work already integrated into `dev`, toward the behaviour the plan already describes, such as `fix/promotion-notice-height`. A defect in a branch that isn't integrated yet is fixed on that branch.
  - `refactor/`: restructures code without changing rendered output, editor settings or behaviour.
  - `chore/`: maintenance with no intended storefront change: dependencies, development tooling and agent configuration, such as `chore/agent-tooling`, and Horizon updates as `chore/horizon-<version>`.
  - `docs/`: changes only to documentation or the plan, such as `docs/plan-store-state`.
  A change that fits two types takes the one with the larger effect on the storefront, in the order above.
- Start a branch from current `dev`, or stack it on its parent where the plan says so. For authorized implementation, verify Git status and the branch's dependencies first, and validate and review the complete diff before local integration. Integrate into `dev` when Chris asks, in the plan's order, with a merge commit: `git switch dev` and `git merge --no-ff <branch>`, keeping Git's message `Merge branch '<branch>' into dev`. Never fast-forward or squash an integration. Record each integration of a plan row in the plan with an "Update development plan" commit on `dev` after the merge; record another branch there only when it changes a feature's status or a decision.
- Never push `dev` without Chris's approval for that push: during development it updates Primary's published theme (see the development note above). Push the integrated branch with it. Keep `main` for authorized releases.
- A release brings `dev` to `main` through a pull request, for its checks, merged locally with `git merge --no-ff dev` and pushed with Chris's approval; README.md ("Releases") has the steps. From launch, `live` is connected to Primary's live theme. It starts each release identical to `main`, and after that only Shopify's GitHub app commits to it (editor and code-editor saves); apart from Shopify, only the release workflow changes it, and nobody pushes to it by hand. Admin changes on `live` come into the repository through a `chore/live-edits-<date>` branch from `dev` and a signed `live-reviewed/<date>` tag, as README.md describes.
- Keep integrated `feature/*` branches as history. Removing a worktree doesn't include deleting its branch; delete a branch only when Chris names it.
- Commit in logical steps as the work goes, with messages like those on `origin/dev`: a short imperative subject in sentence case that says what changed in plain words ("Add store hours block", "Fix French dates for the 1st"), with no prefix, full stop, body, plan ID or design-system jargon, and no trailers or attribution lines. A plan-only commit is "Update development plan"; README and CHANGELOG updates go in the commit of the change they describe. Measurements and verification belong in the plan and the final report.
- Every commit and merge is SSH-signed and must show as verified on GitHub. Commit with ordinary `git commit` and `git merge` so the repository's settings apply: this repository's `.git/config` names the signing key, which differs from the global default. Never pass `--no-gpg-sign`, override `user.signingkey`, or create commits with plumbing such as `git commit-tree` without `-S`. Check with `git log --format='%G? %h %s'` (every line `G`) before asking to push. Shopify's commits on `live` are the exception: they are unsigned and never reach `dev` or `main`.
- Rewrite or force-push history only when Chris asks. The one standing exception is the release workflow's force push of `main` to `live`. A rewrite keeps Horizon's history, vendor tags and `main` intact, keeps each commit on the day it was made and in order, dates nothing after the push, signs every commit, keeps the integration merges, and is built and checked in a separate clone with a backup bundle before it replaces anything.

## Repowise

[Repowise](https://docs.repowise.dev) keeps a local index of this repository in `.repowise/`: the JavaScript import graph, Git history (ownership, hotspots, files that change together), code health, dead code and searchable pages for each file. Each checkout builds its own with the command in `README.md`, and a linked worktree reads its main checkout's index. The index is gitignored, a post-commit hook refreshes it after each commit, and it runs without a model, with local `fastembed` search, so nothing leaves the machine. Its MCP server is `repowise`; the CLI has the same answers (`repowise ask`, `search`, `context`, `risk`, `why`, `health`, `dead-code`).

- For how, where or why questions about this repository, or to find the files a task involves, ask Repowise first (`get_answer`, `search_codebase`, `get_context`), then read only what it didn't show. Go straight to a file you already know.
- Before changing a shared snippet, asset or Horizon file, check `get_risk` for its owners and the files that change with it; before review or integration, check `get_change_risk` for `dev..HEAD`.
- Its graph doesn't follow Liquid: `render`, `section`, `content_for` and `asset_url` references, section and block types, and assets loaded from Liquid aren't edges, so Liquid files have no dependents there and most `assets/*.js` show as unreachable. Find Liquid dependents with a search, and never treat a dead-code finding as proof that a theme file is unused. Its health and dead-code findings in Horizon's own files are upstream.
- Answers without a model are ranked evidence marked `degraded`; missing evidence isn't a negative finding, and platform behaviour still comes from Shopify's documentation.
- `repowise generate`, a model provider, `repowise publish` and the hosted service send code off this machine or spend; each needs Chris's approval.

## Theme conventions

- This is a buildless Horizon 4.5.0 Liquid theme. Use `layout/` and `templates/` for page composition, `sections/` and `blocks/` for editor components, `snippets/` for shared rendering, `assets/` for CSS/JavaScript, and `config/` for settings.
- As authorized features are developed, update buildless development infrastructure when their actual code demonstrates a useful improvement: local checks, type declarations, editor configuration and narrowly scoped development dependencies. Keep changes proportionate and grounded in implemented code; do not add infrastructure in anticipation of future features. This permission does not itself authorize compilation/bundling, generated storefront assets, new test infrastructure, hooks, CI or store-connected work.
- The `--gamma-*` tokens, type roles, notice shell, badge family and other shared pieces are in `assets/gamma-branding.css`, which `snippets/stylesheets.liquid` loads on every page together with the setting-backed tokens that `snippets/gamma-tokens.liquid` writes on `:root`; any surface may use them without rendering a snippet. Colour tokens are declared again on `color-custom-*` surfaces and on elements with the `gamma-tokens` class, so a shared component that uses them carries that class. Shopify loads `{% stylesheet %}` CSS only for the files in a page's render tree: a surface that relies on another snippet's styles, such as the rental card rules in `snippets/gamma-rental-card-styles.liquid`, must render that snippet. Don't rely on rule order between files; a component's own rule that overrides a shared one needs the higher specificity.
- Follow nearby Horizon code, native custom elements and event interfaces. Keep useful server-rendered content and progressive enhancement. Preserve section/block ownership, schema IDs, merchant settings, accessibility and performance behavior.
- Keep Shopify authoritative for selected variants, numeric money, cart, pickup and locale/resource URLs. Preserve existing English/French string references and native localization forms. Before changing a string's wording, search for its key's uses: the same text can be a visible label, an `aria-label` or a meta description.
- Primary Gamma Red (`settings.color_palette.brand`, currently `#ee2622`) is an approved brand exception to contrast-ratio targets everywhere except fine print, defined as text smaller than 10 CSS pixels. Keep normal contrast requirements for that fine print and document contrast shortfalls accurately. Do not substitute dark Gamma Red solely for contrast outside fine print; the retained `brand_accessible` shade may be used for button hover and pressed states. Configure primary buttons through native theme colour settings and retain Horizon's automatic interaction colours. Preserve keyboard access, visible focus, semantics, reduced motion and non-colour state cues.
- Brand badges (`snippets/gamma-brand-badge.liquid`) are a second approved exception for text of 10 CSS pixels and larger: their background is the manufacturer's colour from the Brand entry, and their text is white unless black's contrast with it is at least three times white's, which keeps black on light colours such as Signal Yellow and never gives white below 2.6:1. Record each Brand's measured ratio; the exception doesn't extend to other text on manufacturer colours.
- For authorized visual work, inspect the current rendered experience and approved references before proposing changes. Pursue deliberate visual hierarchy, typography, spacing, interactive states, responsive layouts, accessible interaction and natural Quebec French/English copy. For substantial new designs or departures, offer concise alternatives and tradeoffs, with a temporary mock-up when useful, and obtain approval; refine routine details autonomously within an approved direction. Use the SCS promotions-page design work as a reference for the theme's evolving visual standard, not as permission for unrelated redesigns or changes to approved brand rules.
- Keep reusable Liquid, JavaScript, CSS and component behavior in the theme; merchant-specific page content, policies, metaobject values, menu entries, translations and assignments belong in authorized Shopify Admin workflows. Do not hardcode store-specific IDs, handles, URLs or content into reusable theme code. French storefront routes are rooted at `/`; English uses `/en`—do not assume `/fr`.
- For nontrivial Liquid, objects, filters, tags, sections, blocks, snippets, templates, schemas, settings, localization, accessibility, performance or platform restrictions, consult current official Shopify resources and applicable Horizon conventions. Use Shopify AI Toolkit, the Shopify Codex plugin, Shopify Dev MCP, Theme Check or relevant official validation when available and appropriate. Do not assume tools are installed or connected; fall back to [Shopify developer documentation](https://shopify.dev/docs/storefronts/themes). Avoid lookups for trivial edits, and do not use store-management capabilities simply because they are exposed.

## Validation and integration

- Use locked dependencies and install with `npm ci --ignore-scripts`. For authorized infrastructure changes, pin new development dependencies and update only the relevant lockfile entries; do not regenerate lockfiles or upgrade other dependencies incidentally. Run local `npm run check:all` (Theme Check, JavaScript type checking, unit tests and staged/unstaged whitespace validation); use `npm run check:json` for structured Theme Check diagnostics. Do not use auto-correction or broad formatting.
- Review all diagnostics. The known Horizon warnings are described in `README.md`; distinguish upstream findings from regressions and report unavailable validation accurately. Do not suppress findings to claim success. Local checks do not prove store behavior.
- Match further verification to the changed risk: focused checks for small edits; relevant French/English routes, responsive widths, keyboard/focus and empty/error states for UI; targeted browser interaction for dynamic components; wider regression for shared high-risk behavior or release gates. Inspect actual rendering and screenshots where useful, using available Chromium/Firefox or a connected browser only after verifying access and preview routing. A screenshot does not prove interaction behavior. Do not make genuine contact, newsletter, order or payment submissions without explicit authorization.
- Distinguish observed results from another agent's claims. Report each meaningful check as passed, failed, blocked or not run, and distinguish feature merge readiness from storefront launch readiness. Where remote previews, browser extensions or tunnels are involved, confirm which host and `localhost` are in use before diagnosing a theme failure.
- For each Horizon update, preserve incoming `README.md` as `README-horizon.md`, `LICENSE.md` as `LICENSE-horizon.md`, and `release-notes.md` as `release-notes-horizon.md`, replacing the previous unmodified vendor copies. Resolve rename conflicts, remove duplicate original filenames, and review before integration; `README.md` is the project README.
- Keep only English/French locales: `en.default.json`, `fr.json`, `en.default.schema.json`, `fr.schema.json`. For every Horizon update, inspect all resulting locale files, remove reintroduced non-English/French files, validate retained JSON and storefront/schema key references, and review that diff before integration. `fr.json` and `fr.schema.json` carry Gamma's Quebec French: compare the incoming files with the previous vendor copies, keep Gamma's text where Horizon's English and French didn't change, apply the glossary and spacing in the development plan (G32, Q18) to new and changed keys, and list those keys with their old and new text for Chris. Keep the `shopify.*` checkout overrides. Any regional English/French file needs a concrete requirement. These locale and vendor-document steps require manual review, with no automatic enforcement; `.shopifyignore` does not prevent Git merges from adding files.
- Evaluate verified stable Horizon source commits on a `chore/horizon-<version>` branch as described in `README.md`; preserve upstream history and deliberate Gamma changes.
