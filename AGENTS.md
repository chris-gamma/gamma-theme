# Location Gamma agent guidance

Shared instructions for Claude Code, Codex, GitHub Copilot and other coding agents working with Chris. Read [README.md](README.md) for task-relevant setup and maintenance context; a Markdown link alone does not establish that its contents were loaded.

## Scope and decisions

- Work inside this repository. Preserve existing edits, historical commits, vendor tags, attribution and [LICENSE.md](LICENSE.md). For authorized implementation, verify Git status and feature dependencies, then start bounded work from the appropriate current `dev` on a descriptive `feature/*` branch; validate and review the complete diff before local integration. Keep `main` for authorized releases.
- Make minimal, targeted changes. Preserve deliberate Gamma customizations; inspect relevant code and history before replacing them. Avoid unrelated refactors, dependency changes, formatting or file edits.
- Resolve technical decisions in this order: explicit user instructions; current Shopify platform requirements and supported behavior; Horizon architecture and conventions; Gamma's established conventions and customizations; general development practices. Identify conflicts explicitly. This order does not authorize unsupported or unsafe implementations, or replacing working Gamma behavior merely because a newer pattern exists.
- Establish whether the task is planning, reviewing, or implementing. Planning and review are read-only unless implementation is explicitly requested: inspect relevant evidence without branch changes, dependency installation, file edits, commits or store mutations. Before implementing, identify the requested outcome, applicable approvals, dependencies, affected surfaces and observable acceptance criteria.
- Do not attempt to resolve bugs or issues in upstream Horizon code. Focus on authorized changes within the Gamma project scope. Do not introduce workarounds or modifications for upstream issues unless explicitly authorized. Review and report upstream issues in the response as appropriate.
- Keep work local. Store authentication, connections, previews, uploads, deployments, publication, synchronization and store changes require explicit authorization, including development and unpublished themes. External service writes and hosting operations also require authorization. Confirm the exact store and operation before an authorized write; never infer a store from a branch name or assume authorization carries over from an earlier task.
- Do not add hooks, scripts, skills, workflows, CI or agent tooling unless explicitly requested or authorized. The buildless-maintenance rule below authorizes relevant local configuration, npm check commands and development dependencies; other tooling still requires explicit authorization.

## Collaboration and context efficiency

- Treat Chris as a capable collaborator. Lead with concrete answers, reason frankly and accurately, challenge questionable assumptions, and distinguish verified facts from inferences. Use the established project context without rehashing it. Be natural and concise rather than flattering, corporate or needlessly cautious. Discuss sensitive subjects plainly when relevant; adapt customer-facing copy, documents and other deliverables to their intended audience.
- Match action to authorization: questions and reviews permit investigation and recommendations, while implementation requests permit the bounded changes they describe. Take initiative within that scope, complete and verify authorized work, and request approval for consequential, irreversible or out-of-scope actions. Distinguish explicit requirements, reasonable inferences and new recommendations; never quietly turn the latter into scope.
- For substantial features, clarify the customer goal, expected behavior, business rules, edge cases and acceptance criteria before coding. Ask only consequential unresolved questions, preferably in small batches with a recommended answer and its tradeoff. Do not re-ask settled decisions, demand cosmetic implementation choices or interrupt work for reversible technical details Chris has delegated.
- When preparing a plan or agent handoff, make its stage, receiving agent/session, relevant branch, store scope, approved decisions, boundaries and verification expectations unambiguous. A continuation needs the changes since the last instruction; a fresh session needs enough self-contained context to proceed. Refer to current repository instructions instead of copying long transcripts or historical snapshots as if they were current facts.
- Keep sessions focused on one coherent task. For unrelated work, recommend Claude Code's `/clear` after preserving essential decisions, file paths, Git state and remaining steps in a concise handoff. For a long continuing task, prefer `/compact` and a focused summary over repeatedly starting from scratch. Do not create session-summary files unless requested.
- Inspect narrowly: search for relevant files or symbols first, read the smallest useful code and documentation scope, and reuse evidence already gathered. Verify current repository, platform and runtime facts before relying on historical notes; never claim access to a session, browser, store or test result that has not been observed. Avoid repeated full-repository scans, redundant tool calls, excessively large outputs and broad web research without a task-specific question. Do not save tokens by skipping necessary investigation, testing, accessibility checks or review.
- Invoke Shopify-specific skills and plugins when specialized Liquid, platform, custom-data or API guidance is actually useful. Avoid loading the Shopify plugin for ordinary Git, CSS, JavaScript, writing or coordination tasks that need no Shopify-specific knowledge. Use targeted official sources and existing local tools; do not disable required project capabilities or alter plugin configuration without authorization.
- For Claude Code, prefer Opus at medium effort for substantive work; raise effort to high for demanding architecture, debugging, design or review. Prefer Sonnet for straightforward coordination and appropriately scoped subagents. Delegate only when independent work will materially help, give subagents tight tasks, and avoid duplicate exploration. These preferences do not override explicit model choices or themselves change Claude Code settings.
- Give short progress updates when useful. Finish with what changed, what was verified, what remains uncertain or untested, and any approval needed. State failures and limitations plainly; do not imply a check passed merely because it was attempted.

## Documentation and tests

- Create documentation, tests, fixtures, reports, plans, examples, verification scripts or testing infrastructure only when the user explicitly requests or authorizes those additions. Requests to implement, fix, refactor, clean up or validate something do not, by themselves, authorize them. General best-practice recommendations, templates and tool suggestions are not user authorization.
- Do not materially expand existing documentation or tests without explicit authorization. Keep authorized additions and changes proportionate to the task.
- Prefer existing tests, validators and development tools. Run appropriate existing checks without creating persistent verification artifacts. Do not add dependencies, frameworks, hooks, workflows or configuration to support unrequested documentation or tests.
- Do not create progress logs, implementation summaries, session reports or similar files. Provide requested explanations and verification results in the conversation.
- When additional documentation or tests would provide significant value, briefly suggest them in the conversation instead of implementing them. Continue already authorized work; ask for clarification only when a genuine blocker requires it.
- Necessary, concise comments explaining non-obvious source behavior are permitted during authorized code changes; avoid redundant commentary. Explicit user requests for documentation or tests take precedence over this default policy.

## Theme conventions

- This is a buildless Horizon 4.4.0 Liquid theme. Use `layout/` and `templates/` for page composition, `sections/` and `blocks/` for editor components, `snippets/` for shared rendering, `assets/` for CSS/JavaScript, and `config/` for settings.
- As authorized features are developed, update buildless development infrastructure when their actual code demonstrates a useful improvement: local checks, type declarations, editor configuration and narrowly scoped development dependencies. Keep changes proportionate and grounded in implemented code; do not add infrastructure in anticipation of future features. This permission does not itself authorize compilation/bundling, generated storefront assets, new test infrastructure, hooks, CI or store-connected work.
- The `--gamma-*` tokens, type roles, notice shell, badge family and other shared pieces are in `assets/gamma-branding.css`, which `snippets/stylesheets.liquid` loads on every page together with the setting-backed tokens that `snippets/gamma-tokens.liquid` writes on `:root`; any surface may use them without rendering a snippet. Colour tokens are declared again on `color-custom-*` surfaces and on elements with the `gamma-tokens` class, so a shared component that uses them carries that class. Shopify loads `{% stylesheet %}` CSS only for the files in a page's render tree: a surface that relies on another snippet's styles, such as the rental card rules in `snippets/gamma-rental-card-styles.liquid`, must render that snippet. Don't rely on rule order between files; a component's own rule that overrides a shared one needs the higher specificity.
- Follow nearby Horizon code, native custom elements and event interfaces. Keep useful server-rendered content and progressive enhancement. Preserve section/block ownership, schema IDs, merchant settings, accessibility and performance behavior.
- Keep Shopify authoritative for selected variants, numeric money, cart, pickup and locale/resource URLs. Preserve existing English/French string references and native localization forms.
- Primary Gamma Red (`settings.color_palette.brand`, currently `#ee2622`) is an approved brand exception to contrast-ratio targets everywhere except fine print, defined as text smaller than 10 CSS pixels. Keep normal contrast requirements for that fine print and document contrast shortfalls accurately. Do not substitute dark Gamma Red solely for contrast outside fine print; the retained `brand_accessible` shade may be used for button hover and pressed states. Configure primary buttons through native theme colour settings and retain Horizon's automatic interaction colours. Preserve keyboard access, visible focus, semantics, reduced motion and non-colour state cues.
- For authorized visual work, inspect the current rendered experience and approved references before proposing changes. Pursue deliberate visual hierarchy, typography, spacing, interactive states, responsive layouts, accessible interaction and natural Quebec French/English copy. For substantial new designs or departures, offer concise alternatives and tradeoffs, with a temporary mock-up when useful, and obtain approval; refine routine details autonomously within an approved direction. Use the SCS promotions-page design work as a reference for the theme's evolving visual standard, not as permission for unrelated redesigns or changes to approved brand rules.
- Keep reusable Liquid, JavaScript, CSS and component behavior in the theme; merchant-specific page content, policies, metaobject values, menu entries, translations and assignments belong in authorized Shopify Admin workflows. Do not hardcode store-specific IDs, handles, URLs or content into reusable theme code. French storefront routes are rooted at `/`; English uses `/en`—do not assume `/fr`.
- For nontrivial Liquid, objects, filters, tags, sections, blocks, snippets, templates, schemas, settings, localization, accessibility, performance or platform restrictions, consult current official Shopify resources and applicable Horizon conventions. Use Shopify AI Toolkit, the Shopify Codex plugin, Shopify Dev MCP, Theme Check or relevant official validation when available and appropriate. Do not assume tools are installed or connected; fall back to [Shopify developer documentation](https://shopify.dev/docs/storefronts/themes). Avoid lookups for trivial edits, and do not use store-management capabilities simply because they are exposed.

## Validation and integration

- Use locked dependencies and install with `npm ci --ignore-scripts`. For authorized infrastructure changes, pin new development dependencies and update only the relevant lockfile entries; do not regenerate lockfiles or upgrade other dependencies incidentally. Run local `npm run check:all` (Theme Check, JavaScript type checking and staged/unstaged whitespace validation); use `npm run check:json` for structured Theme Check diagnostics. Do not use auto-correction or broad formatting.
- Review all diagnostics. The known Horizon warnings are described in `README.md`; distinguish upstream findings from regressions and report unavailable validation accurately. Do not suppress findings to claim success. Local checks do not prove store behavior.
- Match further verification to the changed risk: focused checks for small edits; relevant French/English routes, responsive widths, keyboard/focus and empty/error states for UI; targeted browser interaction for dynamic components; wider regression for shared high-risk behavior or release gates. Inspect actual rendering and screenshots where useful, using available Chromium/Firefox or a connected browser only after verifying access and preview routing. A screenshot does not prove interaction behavior. Do not make genuine contact, newsletter, order or payment submissions without explicit authorization.
- Distinguish observed results from another agent's claims. Report each meaningful check as passed, failed, blocked or not run, and distinguish feature merge readiness from storefront launch readiness. Where remote previews, browser extensions or tunnels are involved, confirm which host and `localhost` are in use before diagnosing a theme failure.
- For each Horizon update, preserve incoming `README.md` as `README-horizon.md`, `LICENSE.md` as `LICENSE-horizon.md`, and `release-notes.md` as `release-notes-horizon.md`, replacing the previous unmodified vendor copies. Resolve rename conflicts, remove duplicate original filenames, and review before integration; `README.md` is the project README.
- Keep only English/French locales: `en.default.json`, `fr.json`, `en.default.schema.json`, `fr.schema.json`. For every Horizon update, inspect all resulting locale files, remove reintroduced non-English/French files, validate retained JSON and storefront/schema key references, and review that diff before integration. Any regional English/French file needs a concrete requirement. These locale and vendor-document steps require manual review, with no automatic enforcement; `.shopifyignore` does not prevent Git merges from adding files.
- Evaluate verified stable Horizon source commits on a feature branch as described in `README.md`; preserve upstream history and deliberate Gamma changes.
